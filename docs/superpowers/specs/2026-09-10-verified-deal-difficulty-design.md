# Verified Deal Catalog and Hidden Difficulty Director

Date: 2026-09-10  
Project: Cascade Solitaire  
Status: design ready for review; implementation must not start until this spec is approved.

## 1. Purpose

Cascade needs a much larger supply of genuinely solvable deals and a difficulty system that does not ask the player to choose a difficulty.

The system must solve four product problems at once:

1. **Standard** should be welcoming for a new player, gradually become more demanding as that player wins, and still keep serving easier games later so the mode never becomes a permanent punishment.
2. **Daily** must always be solvable, identical for every player on the same UTC date, unique across the supported schedule, and become progressively harder from Monday through Sunday.
3. A deal may be called **verified** only when a C++ solver has found an exact solution and that exact solution has been replayed successfully through the production TypeScript `SolitaireGame` rules.
4. The production game must not ship giant solver reports or solution proofs. Runtime data should contain only the compact information needed to choose a verified seed.

This design keeps the public mode names and internal mode IDs already used by the project:

- `winnable` = Standard
- `original` = Classic
- `daily` = Daily

Classic is intentionally unchanged and remains genuinely random.

## 2. Current state and why it is insufficient

The current project has one generated `WINNABLE_SEEDS` list in `src/game/model/winnableSeeds.ts`. It contains 512 seeds generated by `tools/sawayama_solver.cpp`.

Both Standard and Daily currently use that same list:

- `GameSession.selectWinnableSeed()` chooses a random member for Standard.
- `DailyCalendar.getDailySeed()` hashes `algorithmVersion:dailyId` into the same list.
- `GameSession.startDaily()` only checks that the seed belongs to that shared list.

The current generated metadata says `SOLVED`, but the regular test suite only validates the list structure and generated counts. It does not independently replay a solver proof through `SolitaireGame`. If the C++ solver and TypeScript model diverge later, a seed can remain labelled winnable without a regression test proving that the real game can still execute its solution.

The existing C++ solver also canonicalizes tableau columns by sorting them during search and automatically normalizes safe foundation moves. Those optimizations are useful and should stay, but a proof-producing solver must preserve enough mapping information to replay its path against the stable tableau indices used by the real game.

## 3. High-level architecture

The new system has three layers.

### Offline deal factory

A development-only pipeline scans seeds, solves them, emits an exact move proof, replays that proof through `SolitaireGame`, measures difficulty, and accepts only successfully replayed candidates.

### Generated verified catalog

Accepted seeds are partitioned into runtime groups. The production build receives compact seed assets plus small metadata; full proofs and raw solver metrics remain development artifacts.

### Runtime selectors

`StandardDifficultyDirector` selects a Standard bucket from player history and then selects an unseen seed from that bucket. `DailyCalendar` indexes a pre-generated date schedule whose seed was already selected for the correct weekday difficulty band.

No runtime solving is performed in the browser.

## 4. Catalog size

### Standard

The hard release minimum is **50,000 unique verified Standard seeds**.

Initial target partition:

| Bucket | Count | Candidate difficulty region |
| --- | ---: | --- |
| `onboarding` | 5,000 | best human-friendly subset of the easiest region |
| `easy` | 15,000 | remaining low difficulty |
| `medium` | 17,500 | middle difficulty |
| `hard` | 12,500 | upper difficulty, excluding pathological extreme tail |
| **Total** | **50,000** | |

The highest approximately 5% of candidate difficulty is not shipped in Standard v1. A deal being solvable does not mean it is a good product deal.

### Daily

The hard minimum is 25,000 unique Daily seeds. The preferred generation target is **36,525 unique verified Daily seeds**, enough for roughly 100 years of one unique deal per UTC calendar day.

Daily seeds must be disjoint from every Standard seed.

The generator should use separate source ranges for reproducibility and accidental-overlap prevention. The initial ranges are:

- Standard candidates: starting at seed `1`
- Daily candidates: starting at seed `1_000_000_001`

The factory must still explicitly assert cross-catalog uniqueness instead of relying only on the source ranges.

All generated catalog seeds are constrained to positive uint32 values. The current RNG accepts them as `bigint`, and uint32 storage makes the production catalog compact while leaving billions of possible candidates.

## 5. What “verified” means

A seed receives `VERIFIED` status only after all of these stages succeed:

```text
seed
  -> C++ deal generation
  -> C++ search finds a complete solution
  -> solver emits exact proof actions
  -> TypeScript verifier creates the same deal through createDealForMode()
  -> verifier executes every proof action through SolitaireGame
  -> every action is legal and produces the expected card/state transition
  -> SolitaireGame.isWon === true
  -> candidate becomes VERIFIED
```

`UNDETERMINED` is never treated as unsolvable and never enters a catalog. The factory may retry it with a larger search budget and otherwise discard it.

The initial search strategy is two-pass:

1. fast pass with the current 250,000-node budget;
2. retry unresolved candidates with up to 2,000,000 nodes.

The generator continues scanning until the required verified quotas are filled; it does not assume a fixed solved ratio.

## 6. Proof format and solver changes

The C++ solver must produce a proof in game-level actions, not only a final state.

Conceptual action types:

```text
DRAW
MOVE_TABLEAU(sourceStablePile, startCardId, destinationStablePile)
MOVE_WASTE_TO_TABLEAU(cardId, destinationStablePile)
MOVE_FREE_TO_TABLEAU(cardId, destinationStablePile)
MOVE_TO_FREE(source, cardId)
MOVE_TO_FOUNDATION(source, cardId, suit)
```

Safe foundation moves performed by solver normalization must also appear in the proof as explicit `MOVE_TO_FOUNDATION` actions. The TypeScript verifier must not silently assume that a normalization step happened.

### Stable tableau identity

The current solver sorts tableau columns to canonicalize equivalent states. Proof generation must preserve that optimization.

Each solver column therefore carries a `stablePileId` corresponding to the original TypeScript tableau index `0..6`. Sorting reorders `(cards, stablePileId)` pairs together. State hashing may continue to ignore the stable IDs so column permutations remain canonical, while emitted proof actions use the stable IDs.

When two equivalent canonical states are reached by different permutations, the search may keep the first representative. Its stable-ID mapping is sufficient because tableau columns are mechanically symmetric; the proof only needs one replayable representative path.

### Proof replay checks

The verifier must validate more than a boolean return value. For every action it should check relevant invariants such as:

- expected source card ID is currently exposed or begins the expected movable run;
- `draw()` exposes the same card order recorded by the proof;
- a requested move returns `true`;
- foundation count changes as expected;
- all 52 cards remain unique across tableau, stock, waste, free cell, and foundations;
- the final state has all 52 cards in foundations.

A corrupt proof must fail loudly with the seed and action index.

## 7. Development artifacts vs production assets

Detailed solver output is development-only. It may contain:

- seed;
- solver status and visited nodes;
- proof actions;
- measured solution metrics;
- computed difficulty score;
- rejection reason if verification fails.

These files should live under an ignored `artifacts/deals/` directory and use append/checkpoint-friendly JSONL or another resumable format. A long generation run must be resumable after interruption.

The committed production output contains only:

- compact Standard seed buckets;
- the pre-generated Daily date schedule;
- catalog/version metadata;
- a small committed proof fixture sample used by regular regression tests.

Recommended production representation is a simple generated binary format containing uint32 seeds plus bucket offsets. Approximate payload at the release minimum is only a few hundred kilobytes before HTTP compression, and it avoids adding tens of thousands of numeric literals to the main JavaScript bundle.

The loader exposes typed read-only access; the rest of the game should not know the binary representation.

## 8. Difficulty measurement v1

Solver search effort alone must not define human difficulty. It is retained as one signal, because it is useful, but the factory also measures the verified solution path.

For every verified candidate, collect at least:

- `solverNodes`: nodes visited before finding the proof;
- `decisionActions`: proof actions excluding automatic safe-foundation normalization;
- `rearrangementMoves`: moves whose destination is tableau or free cell rather than foundation;
- `freeCellTouches`: moves into or out of the free cell;
- `stockInterleaves`: non-draw decisions made while stock is still present between draw operations;
- `earlyProgressActions`: decision actions required to place the first four cards into foundations.

Each metric is converted to a percentile within the generated candidate population. `solverNodes` is transformed with `log1p` before percentile ranking so a few pathological searches do not dominate.

The initial v1 composite score is:

```text
30%  solverNodes percentile
25%  rearrangementMoves percentile
15%  freeCellTouches percentile
15%  stockInterleaves percentile
10%  decisionActions percentile
 5%  earlyProgressActions percentile
```

The score is an offline ranking tool, not a claim of mathematically exact human difficulty. After launch, real win rate, restart/abandon rate, completion time, hint usage, and undo usage can be used to recalibrate bucket boundaries in a later catalog version.

Changing difficulty weights does not invalidate the fact that a seed is verified; it only changes classification.

## 9. Onboarding deals

For players with fewer than three Standard wins, Standard uses the dedicated `onboarding` bucket rather than the general easy bucket.

The onboarding bucket is selected from the easiest candidate region but also applies human-friendly filters. Prefer candidates with:

- low composite score;
- low free-cell dependence;
- low rearrangement count;
- early foundation progress;
- a useful stock/tableau action appearing early rather than a long dead-looking opening.

The factory keeps scanning until 5,000 deals satisfy the onboarding quota. It must not weaken verification to fill that quota.

A player remains in onboarding until the **third Standard win**, not until the third attempt. A struggling player therefore cannot age out of the easy introduction merely by losing or abandoning games.

## 10. Hidden Standard difficulty director

Difficulty is never shown as a player-selectable setting. The player simply presses Standard.

The base bucket distribution depends on completed Standard wins (`metaState.stats.winnable.wins`):

| Standard wins | Easy | Medium | Hard |
| ---: | ---: | ---: | ---: |
| 0–2 | onboarding only | — | — |
| 3–5 | 85% | 15% | 0% |
| 6–10 | 65% | 35% | 0% |
| 11–20 | 45% | 45% | 10% |
| 21–40 | 30% | 50% | 20% |
| 41+ | 25% | 45% | 30% |

Even a highly experienced player always retains at least a 25% easy chance.

### Failure softening

Difficulty rank never visibly decreases and Standard wins are never removed. Instead the director has a hidden consecutive-failure streak.

A Standard failure is recorded only when a **started, unfinished Standard attempt is deliberately discarded and replaced** by another deal/mode. The following do not count as failures:

- opening/closing the menu;
- browser refresh or restoring a checkpoint;
- pausing and resuming;
- restarting the same seed.

Rules:

- 0–1 consecutive failures: use the base distribution;
- exactly 2 consecutive failures: make the base roll, then with 70% probability soften it one tier (`hard -> medium`, `medium -> easy`);
- 3 or more consecutive failures: force `easy` until the next Standard win;
- any Standard win resets the failure streak to zero.

If the player still has fewer than three Standard wins, onboarding takes precedence over the failure rules.

### No consecutive hard deals

If the last served Standard tier was `hard`, the next Standard selection cannot be `hard`. Any hard result is rerolled between easy and medium using their normalized probabilities.

### Repeat avoidance

The profile stores the most recent **256 Standard seeds served**. Selection rejects those seeds. With a 50,000-deal pool this prevents perceptible repetition without bloating cloud storage.

If a bucket somehow has no candidate outside recent history, the selector progressively forgets the oldest history entries rather than failing to start a game.

The history records a seed when it is served, not only when it is won, so repeatedly abandoning a deal cannot cause it to be immediately reissued.

## 11. Standard persistence

The hidden director state is persisted with player meta data so it follows cloud saves.

Add a new Standard difficulty section to the next `MetaSave` version containing only data that cannot already be derived from existing stats:

```text
standardDifficulty:
  failureStreak: integer 0..3
  lastServedTier: onboarding | easy | medium | hard | empty
  recentSeeds: string[]  // max 256 positive uint32 seed strings
```

Do **not** duplicate Standard win count; use existing `stats.winnable.wins`.

Updates that affect this state must go through the existing journal/session persistence model so cloud replay stays idempotent. Serving a Standard deal, abandoning a started Standard attempt, and completing a Standard win are explicit meta operations.

A restart of the same deal creates no served-deal operation and no failure operation.

Existing saves migrate with:

- `failureStreak = 0`;
- empty `lastServedTier`;
- empty `recentSeeds`;
- existing `stats.winnable.wins` preserved and immediately used for the base curve.

Thus an existing experienced profile is not treated as a brand-new player merely because the difficulty system is new.

## 12. Daily schedule

Daily does not adapt to the player. Every player running the same Daily algorithm version receives exactly the same seed for the same UTC `dailyId`.

Difficulty target by UTC weekday:

| Day | Candidate score percentile |
| --- | --- |
| Monday | 0–15 |
| Tuesday | 10–30 |
| Wednesday | 25–45 |
| Thursday | 40–60 |
| Friday | 55–72 |
| Saturday | 68–85 |
| Sunday | 80–95 |

The overlap is deliberate: adjacent weekdays should trend upward without every Monday or Sunday feeling identical. The top 5% is never scheduled in Daily v1.

### Pre-generated schedule, not runtime hashing

The current `stableHash32(date) % pool.length` approach is replaced by a pre-generated schedule.

The factory walks consecutive UTC dates from a fixed schedule anchor and assigns one unused verified Daily seed whose score lies in that weekday's target band. Selection within a band is deterministically shuffled during generation so difficulty varies naturally inside the allowed range.

A Daily seed is consumed once and cannot appear on another date in the generated horizon.

Preferred initial schedule:

```text
start: 2026-01-01 UTC
length: 36,525 days
```

`getDailySeed(dailyId)` becomes an index lookup by UTC day offset. Dates outside the committed schedule must throw a clear error rather than silently fall back to an unverified or repeated seed.

The schedule duration is intentionally much longer than the expected lifetime of this release generation so this failure should never occur in normal use.

## 13. Daily algorithm migration and fairness

Changing from the current shared 512-seed hash to the verified date schedule requires a new Daily algorithm version.

Set `DAILY_ALGORITHM_VERSION` to the next version when the schedule ships. For **new Daily starts**, selection uses the code's current algorithm version, not a stale version retained by an old profile.

Old Daily completion records remain valid history. An old active Daily checkpoint whose algorithm version does not match the current shipped version is not resumed as the new Daily challenge.

Daily algorithm versions should not be changed casually. A schedule/version update should be released at a UTC day boundary where practical, because changing the Daily seed during the same calendar day would undermine leaderboard fairness.

## 14. Runtime APIs and responsibilities

### `VerifiedDealCatalog`

Responsible for loading generated runtime assets and exposing:

```text
getStandardSeeds(tier)
hasStandardSeed(seed)
getDailySeedByOffset(dayOffset)
hasDailySeed(seed)
metadata/version information
```

It owns binary decoding. No game-rule logic belongs here.

### `StandardDifficultyDirector`

Pure logic. Input:

- Standard win count;
- failure streak;
- last served tier;
- recent seeds;
- entropy source;
- Standard catalog.

Output:

- selected tier;
- selected seed;
- updated served-deal history state.

It has no Phaser dependency and is exhaustively unit-testable.

### `DailyCalendar`

Keeps existing UTC day/week responsibilities but reads the generated date schedule instead of hashing into the shared Standard pool.

### `GameSession` / `GameFlow`

`GameSession` should stop owning a generic `WINNABLE_SEEDS` array. Verified Standard and Daily seeds are selected before deal creation and passed into the session through explicit verified-start paths. Classic keeps its own random seed generation.

Validation remains defensive: Standard start rejects a seed not in the Standard catalog; Daily start rejects a seed not in the Daily schedule/catalog.

### `GameScene`

Orchestrates only:

- ask director for a Standard deal when needed;
- dispatch journaled served/abandon/win meta operations;
- pass selected seed to flow/session;
- preserve the existing active-game checkpoint behavior.

Difficulty math and seed-pool details must not be implemented inside `GameScene`.

## 15. Generation commands

The exact script names may follow project conventions, but the finished workflow should expose these stable responsibilities:

```text
pnpm deals:build-solver
pnpm deals:generate
pnpm deals:verify-sample
pnpm deals:verify-all
pnpm deals:report
```

`deals:generate`:

- scans candidate ranges in parallel;
- supports configurable worker count;
- checkpoints progress;
- retries undetermined seeds with the slow budget;
- proof-verifies every accepted candidate through TypeScript;
- computes difficulty metrics;
- fills Standard and Daily quotas;
- writes production catalog assets and a manifest only after all invariants pass.

Compiler discovery must not be hard-coded solely to one Windows path. The build wrapper should support an explicit `CXX`/solver override and sensible platform fallback. The user's current MSYS2 UCRT g++ remains a supported path, not the only path.

## 16. Generated manifest

Commit a small manifest next to the runtime catalog containing at least:

```text
catalogVersion
difficultyModelVersion
dailyAlgorithmVersion
solverSourceHash
gameRulesSourceHash
standardCounts by tier
dailyScheduleStart
dailyScheduleLength
fastNodeBudget
slowNodeBudget
source scan ranges
verified count
rejected verification count
cross-pool duplicate count (must be 0)
production asset hash
```

This gives us an auditable answer to “which solver/rules produced these deals?” without committing the huge proof report.

## 17. Tests and verification gates

### Regular `pnpm test`

Keep this fast. It must cover:

- catalog parser and manifest integrity;
- expected Standard counts;
- all production Standard/Daily seed IDs are positive uint32;
- no duplicate seeds within a bucket/schedule;
- no overlap between Standard and Daily;
- director table boundaries at 0/3/6/11/21/41 wins;
- onboarding remains active until three wins;
- two-failure softening;
- three-failure easy guarantee;
- a win resets failure streak;
- restart does not count as failure;
- no two hard deals in succession;
- recent seed rejection and fallback behavior;
- same Daily date always maps to the same scheduled seed;
- weekday schedule entries fall in their intended score band according to generation metadata/fixtures;
- a corrupt proof fixture is rejected;
- committed proof sample successfully replays through `SolitaireGame`.

### Committed proof sample

Commit a representative sample of proofs, not all proofs. It should cover all Standard tiers and all seven Daily weekday bands. Approximately 64–128 representative seeds is enough for the normal regression suite.

This is the fast alarm for future rule drift.

### Full verification gate

`pnpm deals:verify-all` is a release/regeneration gate, not part of every edit-test cycle. It re-solves/reconstructs proof paths for every production seed and replays them through the current `SolitaireGame`.

A release must not regenerate or ship the catalog if any production seed fails replay.

## 18. Acceptance criteria

Implementation is complete only when all of the following are true:

1. Standard ships with at least 50,000 unique verified seeds.
2. Daily ships with at least 25,000 unique verified seeds; preferred release target is the 36,525-day schedule.
3. Standard and Daily have zero seed overlap.
4. Every catalog seed was accepted only after a C++ proof successfully replayed through the TypeScript `SolitaireGame`.
5. A reproducible manifest records solver/rules/catalog versions and hashes.
6. Players with fewer than three Standard wins receive only onboarding deals.
7. Standard difficulty follows the approved win-based probability curve after onboarding.
8. Two consecutive failures soften selection; three force easy; a win resets the streak.
9. Hard is never served twice in a row.
10. Easy remains at least 25% of the base distribution for 41+ Standard wins.
11. Standard avoids the last 256 served seeds.
12. Daily is identical for all players on the same UTC date and is not player-adaptive.
13. Daily difficulty trends Monday -> Sunday using the specified percentile bands.
14. No Daily seed repeats within the generated schedule horizon.
15. Classic behavior is unchanged.
16. Regular tests remain fast; full-catalog proof verification exists as a separate release command.
17. No player-facing difficulty selector or difficulty label is introduced.

## 19. Explicit non-goals

This work does not add:

- a difficulty selector;
- rubber-banding inside an already-started deal;
- runtime browser solving;
- a second currency or progression system;
- new game rules;
- changes to Classic randomness;
- player-facing explanations that the game is secretly adapting difficulty.

The director changes only **which already-verified deal is served next**.

## 20. Rollout order

Implement in this order so each stage can be verified independently:

1. proof-producing C++ solver with stable tableau mapping;
2. TypeScript proof verifier against `SolitaireGame`;
3. metric extraction and difficulty model;
4. resumable catalog generator and production asset format;
5. generate and verify the large Standard catalog;
6. generate the long Daily schedule and bump Daily algorithm version;
7. StandardDifficultyDirector and MetaSave migration;
8. wire Standard selection and failure events into session/scene;
9. fast regression sample + full verification command;
10. run full test/build and manually smoke Standard onboarding, advanced Standard, restart/abandon, Daily, save/restore, and leaderboard flows.

No later stage is allowed to weaken the `VERIFIED` definition to make quota generation easier.
